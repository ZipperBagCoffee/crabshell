# Verification runner reuse, timing and output

Read the relevant section when Run Mode in `SKILL.md` points here.

## Reuse and timing

**Reuse.** A selected check reuses PASS when its key matches: normalized entry, runner bytes, Node version, platform, architecture, test bytes and input hashes (folders use sorted names). Fingerprints taken immediately before each check must match after it passes; newly traced inputs must predate its start. Changed or unreadable inputs get no key. `passedAt` expires after seven days; reuse does not renew it.

Never reuse failed or timed-out checks, manual entries, empty input records, `always: true`, `reuse: false`, explicit entry IDs, changed tests requiring fail-before, or full `--changed` fallbacks. `--no-reuse` forces all selected checks to execute. Discovery entries can use `reuseExclude` to disable reuse for individual files; use these controls for external tools or other untracked inputs (see [manifest entry controls](manifest-entries.md)).

**Coverage.** `coveredBy` names a check that also runs this test. When both are selected and the child has a nonempty file record, the covering check runs first. Its executed or reused PASS records the child as `status: "PASS"`, `coveredBy: "<id>"`, `durationMs: 0`, without `reused` or an independent pass key. For a child with `reuse: false`, `reuseExclude` or `always: true`, only a covering check that actually executed and passed in this run permits coverage; a reused PASS makes the child execute. A failed or timed-out covering check also forces the child to execute, even if it has an older cached PASS. Results keep manifest order. Established dependency records and execution durations are retained. A missing record, missing `files` or empty `files` makes the child execute to establish its own inputs first.

Coverage is disabled when the covering check is absent, an ID is explicitly named, `--no-reuse` is given, or the child test changed and fail-before is enabled. This last rule conservatively includes changed tests before their newly traced inputs are known. A covered result cannot cover another check in a chain; that child executes. Unknown IDs and coverage cycles are manifest errors. A covered entry or discovered file must have no `contract.assertions`, and every path in its `contract.forbiddenChanges` must also occur in the covering check's list; violations name both IDs. Declaration shapes are in [manifest entry controls](manifest-entries.md).

`--dry-run` prints JSON without executing: `reasons` for each selection, `wouldReuse` and `wouldCover` counts, and `estimatedSeconds` from durations of checks that would execute (unknowns contribute zero). Coverage estimates assume the covering check passes and exclude the covered child's duration; selection reasons stay unchanged. Results carry `durationMs`; the map keeps `lastDurationMs` from execution. Reuse and coverage report zero without replacing it.

## Manifest changes in changed-file mode

`planChanged` compares the manifest with what `test-map.json` recorded, even when Git reports no manifest change. Each record has `entryHash`, the SHA-256 of the manifest entry's JSON (the discovery entry's JSON for a discovered check). Missing or different entry hashes select those checks, with reason `manifest entry <id> changed`; new checks remain selected. Changed manifest content also selects checks whose recorded inputs cover the manifest path. Other changed-file readers remain selected as usual. Removed entries need no execution. Unchanged entries may still reuse PASS.

The map's `manifestHash` is the SHA-256 of normalized top-level fields other than `entries`, `created` and `updated`. A missing hash causes a full fallback with `load map has no manifest record`; a different hash gives `manifest field changed since the load map`. Full fallback selects every check and disables cached reuse, but eligible covered checks may still skip execution when their covering check passes. Runner changes and existing missing/stale-map and unknown-input fallbacks still apply; the manifest uses hash comparison instead of the timestamp-based stale-map fallback.

Only checks that pass in the current run (executed, reused or covered) update their `entryHash`; unselected and failed records keep their prior hashes. `manifestHash` updates only on a successful full map write. Partial runs and mixed failures retain it. Thus an entry changed by a pull, rebase or commit without a run stays selected, including when another entry is later edited locally. `created` and `updated` do not affect these hashes, but manifest readers still see their content changes.

## Output and saved results

Default stdout shows a one-line verdict: executed/reused counts, `N covered by <id>` (or `N covered by other checks` for multiple covering IDs), manual checks waiting for a person, elapsed seconds; zero parts are omitted. Covered checks count as PASS, not as executed. Failures show their first failure line and last five stderr lines. Empty selection says `No checks selected — nothing changed that a check reads.` and exits 0. `Verification Results: PASS: N / FAIL: N / Manual: N / Total: N` remains.

For a person's nonempty run (full, `--changed`, `--json` or explicit ID), the full array is saved atomically to `last-run.json` beside the runner: `Full results: <path>` confirms success; `Full results: not saved (<error>)` reports failure. Internal calls with `CRABSHELL_VERIFY_JSON=1` or `--no-fail-before`, and runs producing no results, leave the previous file byte-identical and print no `Full results:` line. Read the saved file instead of rerunning. `--json` or `CRABSHELL_VERIFY_JSON=1` also prints the current array; `--no-fail-before` does so for older guards. `--changed --json` does **not** count for the commit gate: use the declared `--changed` command and its saved JSON.
